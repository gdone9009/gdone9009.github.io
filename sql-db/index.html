제3정규형 (3NF)

👤 members (회원)

  • 🔑 member_id: INTEGER (PK)
  • 📌 name: TEXT (NOT NULL)
  • ✨ email: TEXT (UNIQUE, NOT NULL)
  • 📞 phone: TEXT
  • 📅 join_date: DATE (DEFAULT today)

🏷️ categories (카테고리)

  • 🔑 category_id: INTEGER (PK)
  • ✨ category_name: TEXT (UNIQUE, NOT NULL)

📚 books (도서)

  • 🔑 book_id: INTEGER (PK)
  • 📌 title: TEXT (NOT NULL)
  • ✍️ author: TEXT (NOT NULL)
  • 💰 price: INTEGER (NOT NULL)
  • 🔗 category_id: INTEGER (FK ➔ categories)

📑 rentals (대여 이력)

  • 🔑 rental_id: INTEGER (PK)
  • 🔗 member_id: INTEGER (FK ➔ members)
  • 🔗 book_id: INTEGER (FK ➔ books)
  • 📅 rental_date: DATE (DEFAULT today)
💡 1:N 관계 해설:
• categories (1) : books (N) — 하나의 카테고리에는 여러 권의 도서가 포함됩니다.
• members (1) : rentals (N) — 한 명의 회원은 여러 번 대여할 수 있습니다.
• books (1) : rentals (N) — 한 권의 도서는 시간에 따라 여러 번 대여될 수 있습니다.

📘 관계형 데이터베이스 기초 학습 매뉴얼

1. 엑셀(Excel)과 데이터베이스(RDBMS)의 본질적 차이

엑셀은 데이터를 자유롭게 적는 스프레드시트이지만, 데이터가 커질수록 중복 입력과 참조 오류가 발생하기 쉽습니다. 반면 관계형 데이터베이스(RDBMS)는 다음과 같은 핵심 장점을 가집니다:

  • 데이터 무결성(Integrity): PK, FK, NOT NULL, UNIQUE 등의 규칙을 엔진 수준에서 강제합니다.
  • 동시성 제어(Concurrency): 수백, 수천 명의 사용자가 동시에 읽고 쓸 때 데이터 충돌을 방지합니다.
  • 표준 쿼리 언어(SQL): 대용량 데이터에서 원하는 조건의 데이터를 $O(\log N)$ 인덱스로 빠르게 조회합니다.

2. 제3정규형(3NF) 설계 원칙

데이터 중복에 따른 이상 현상(삽입 이상, 갱신 이상, 삭제 이상)을 방지하기 위해 도서 관리 시스템은 다음 3단계를 거쳐 4개 테이블로 분리되었습니다:

  1. 제1정규형 (1NF): 모든 컬럼의 값이 하나의 원자값(Atomic Value)을 갖도록 분리.
  2. 제2정규형 (2NF): 기본 키의 진부분집합에 종속되는 부분 함수 종속성 제거.
  3. 제3정규형 (3NF): 기본 키가 아닌 일반 컬럼 간의 이행적 함수 종속($X \to Y \to Z$) 제거.

3. 인덱스(Index)의 작동 원리와 필요성

인덱스는 책의 맨 뒤에 있는 '색인(Index)'과 같습니다. 인덱스가 없으면 100만 건의 데이터를 모두 읽는 풀 테이블 스캔(Full Table Scan, $O(N)$)이 발생하지만, 외래키 컬럼(books.category_id)에 B-Tree 인덱스를 생성하면 $O(\log N)$의 고속 검색이 가능해집니다.

💬 기술 면접 및 평가 대비 핵심 질의응답 (Q&A)

Q1. 1:N 관계를 맺을 때 외래키(FK)는 왜 'N(자식)' 쪽에 위치해야 하나요?
답변: 1(부모) 쪽에 외래키를 두면 한 행에 여러 개의 자식 ID를 콤마 등으로 묶어 저장해야 하므로 제1정규형(1NF, 원자값 원칙)을 위반하게 됩니다. 반면 N(자식) 쪽에 부모의 PK를 FK로 저장하면 모든 레코드가 단일 원자값을 유지하면서 자연스러운 1:N 조회가 가능해집니다.
Q2. INNER JOIN과 LEFT JOIN의 차이는 무엇인가요?
답변: INNER JOIN은 양쪽 테이블 모두에 조건이 일치하는 행만 결과로 반환합니다. 반면 LEFT JOIN은 왼쪽(기준) 테이블의 모든 행을 유지하며, 오른쪽 테이블에 매칭되는 데이터가 없으면 NULL로 채워 결과를 반환합니다. (예: 대여 이력이 없는 회원도 목록에 표시할 때 LEFT JOIN 활용)
Q3. 보너스 1 과제에서 JOIN 방식과 서브쿼리 방식의 차이는 무엇인가요?
답변: 가독성 측면에서 단순 스칼라 조건 치환은 서브쿼리가 직관적이지만, 대용량 RDBMS 환경에서는 옵티마이저(Optimizer)가 JOIN 조건절에 대해 인덱스 결합(Nested Loop, Hash Join)을 유연하게 수립할 수 있어 실무 대규모 쿼리에서는 JOIN 방식이 성능 면에서 우수합니다.
